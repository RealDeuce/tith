1. Introduction
───────────────

  There have been many different ways to express a FidoNet address
  over the years.  All TITH protocols will use a single well defined
  text encoding.


2. Components
─────────────

  Every node address has five components, which all contain values
  specified in this document.  These five components are:

  Domain
  ──────
  The domain is a nonempty UTF‑8 string.  It does not contain a code
  point from U+0000 through U+001F or U+007F through U+009F, the Number
  Sign (U+0023), the Asterisk (U+002A), the Comma (U+002C), the
  Less‐Than Sign (U+003C), or the Greater‐Than Sign (U+003E).

  The Domain MUST NOT begin or end with any of U+0009 through U+000D,
  U+0020, U+0085, U+00A0, U+1680, U+2000 through U+200A, U+2028,
  U+2029, U+202F, U+205F, or U+3000.  These are the code points treated
  as whitespace by this document.

  The canonical domain name for FidoNet is "fidonet".  Tools often use
  a domain as part of a file or directory name.  Operators should
  therefore consider filename portability when assigning one.  Code
  points commonly troublesome for that use include U+003A (':'),
  U+0022 ('"'), U+002F ('/'), U+005C ('\'), U+007C ('|'), and U+003F
  ('?').  This is operational guidance and does not remove those code
  points from the Domain grammar.

  The literal Domain "p2p" is reserved for the nodelist‐free
  peer‐to‐peer network described in TRD‑0003.  Its only valid address
  is the anonymous address "p2p#-1".  A producer MUST NOT construct,
  and a consumer MUST reject, a "p2p" address with any other Zone.

  Example domains "fidonet", "БорМер"

  Zone
  ────
  The zone is a number that is either negative one, or a value from
  one to thirty‐two thousand, seven hundred and sixty‐seven
  inclusive (−1, 1–32,767).

  Net
  ───
  The net is a number that is either negative one, or a value from one
  to thirty‐two thousand, seven hundred and sixty‐seven inclusive
  (−1, 1–32,767).  If the Zone is negative one (−1), Net MUST also be
  negative one (−1).  If the Zone is not negative one (−1), the Net
  MUST NOT be negative one (−1).

  Node
  ────
  The node is a number in the range of negative one to thirty‐two
  thousand, seven hundred and sixty‐seven (−1–32,767).  If the Zone is
  negative one, the Node MUST also be negative one (−1).  If the Zone
  is not negative one (−1), the Node MUST NOT be negative one (−1).

  Point
  ─────
  The point is a number in the range of zero to sixty‐five thousand,
  five hundred and thirty‐five (0–65,535).  If the Zone is negative
  one, the Point MUST be zero (0).


3. Default Values
─────────────────

  Domain and Zone do not have a default value.  An input without both
  is not a TITH address.  A conversion specification may define trusted
  context which supplies facts absent from another address format, but
  the result is a complete address governed by this document before it
  enters native processing.

  The Net and Node have a default value that depends on the value of
  the Zone.  If the Zone is negative one (−1), the default for the
  Net and Node is also negative one (−1).

  If the Zone is not negative one (−1), the default Net is the same
  value as the Zone, and the default Node is zero (0).

  The default Point is always zero (0).


4. Encoding as Text
───────────────────

  All text node addresses begin with the Domain and Zone separated by
  a Number sign (U+23 '#').

  The rest of the components MUST NOT be included if they have the
  default value from section 3.

  If included, the Net, Node, and Point values each have a specific
  code point prefix introducing them.  The prefix for Net is U+3A
  (':'), the prefix for Node is U+2F ('/'), and the prefix for Point
  is U+2E ('.').

  Components other than Domain are represented as decimal values,
  either as the literal string "-1" (U+2D, U+31) if the value is
  negative one (−1) or with a code point from U+31 ('1') to U+39 ('9')
  followed by zero or more code points from U+30 ('0') to U+39 ('9').
  That is to say that leading zeros are not allowed, and negative one
  (−1) has a single legal encoding.  In the cases where zero (0) is a
  legal value, it is also the default, so will not be encoded.

  Examples:
  ─────────
  The broken‐down value of the address in these examples has the
  values separated by commas with a prefix of Z, N, O, and P for the
  Zone, Net, Node, and Point value respectively.

  "fidonet#1" would represent fidonet, Z1, N1, O0, P0 (AKA Z1C)
  "fidonet#1:10" would represent fidonet, Z1, N10, O0, P0 (AKA R10C)
  "fidonet#1/2" would represent fidonet, Z1, N1, O2, P0
  "fidonet#1.5" would represent fidonet, Z1, N1, O0, P5
  "fidonet#-1" would represent fidonet, Z−1, N−1, O−1, P0.

  A public key, for the purposes of a TITH identity, is the 32 binary
  bytes of a Libhydrogen signing public key as specified by the exact
  Version 1 reference in appendix A.

  The address whose Zone is negative one (−1) is the anonymous address
  for its Domain and MUST NOT appear in a nodelist.  Since it does not
  uniquely identify a system, it MUST be associated with a public key
  whenever it is used to identify a system.  A prospective node may
  use the anonymous address while applying for a non‐anonymous address.
  In the "p2p" Domain it is instead the permanent address of every
  system.

  An address is anonymous or non‐anonymous solely according to this
  encoding.  A non‐anonymous identity is identified by its address.
  An anonymous identity is the exact pair of its anonymous address and
  associated public key.  Different public keys at the same anonymous
  address identify different systems.

  Listing is a separate, observer‐relative trust state.  An identity is
  listed for an implementation when its address appears in the current
  nodelist or its exact identity has an effective local key pin
  established by explicit trust policy.  It is unlisted otherwise.  A
  nodelist entry lists its identity whether or not the entry contains a
  public key.  Merely receiving an accompanying public key MUST NOT by
  itself establish a pin.  Consequently an anonymous identity may be
  either listed or unlisted, and a non‐anonymous identity absent from a
  nodelist may likewise be listed by a pin.

  Protocol grammar which depends on the address encoding MUST use the
  terms anonymous and non‐anonymous, not listed and unlisted.  A
  protocol MAY use listing status for local trust or policy decisions.
  The representation of a local pin is implementation‐private unless
  another standard specifies its required behaviour.


5. Trimmed Collections
──────────────────────

  Some components of FTN such as SEEN‑BY use "Trimmed Collections" of
  node addresses.  These lists are sorted and have redundant
  components eliminated to keep the overall size of the list as small
  as possible.  This section defines how such a list is constructed.

  An empty collection is encoded as an empty string.  Otherwise, exact
  duplicate addresses are first removed.  A Trimmed Collection is a
  set; unlike a Trimmed List, repeated occurrences do not carry
  information.

  The remaining addresses are sorted.  The sort order of Domains is
  based on a binary comparison of the unsigned value of each byte of
  the UTF‑8 encoding starting with the first byte.  The lower byte
  value is sorted first.  If a byte is not present in one of the two,
  the domain without the byte is sorted first (ie: "fido" is sorted
  before "fidonet").  The other fields are sorted by ascending numeric
  value (ie: 9 is sorted before 10, and −1 is sorted before 1).

  The first address is emitted in the complete canonical form from
  section 4.  For each later address, find the first component whose
  expanded value differs from the previous address.  Emit that
  component with its prefix.  Components above it are inherited from
  the previous address.  Components below it are reset to the defaults
  in section 3 and are then emitted, in component order, when their
  values in the new address differ from those defaults.

  Finally, each element is listed in order, separated by a single Comma
  (U+002C, ',').  On input, an element beginning with a prefix inherits
  the higher components, sets its named component, resets the lower
  components, and then applies any following components in increasing
  order.  The first element MUST be complete.  An empty element, a
  component without a value, or a repeated or out‐of‐order prefix is
  invalid.

  An encoding is a canonical Trimmed Collection only when expanding it
  and applying the complete construction above reproduces the exact
  input bytes.  This rejects an unsorted collection, a duplicate, an
  unnecessarily complete later address, and any other redundant
  spelling.

  Example: fidonet#1,fidonet#1:2,fidonet#1:2/103,BBSDev#885:1/1,
  fidonet#1:2/103.1,BBSDev#885,BBSDev#885:1,BBSDev#885:1/1,
  BBSDev#885:1/2

  Would first have the duplicate BBSDev#885:1/1 removed and be sorted
  to: BBSDev#885:1,BBSDev#885:1/1,BBSDev#885:1/2,BBSDev#885,
  fidonet#1,fidonet#1:2,fidonet#1:2/103,
  fidonet#1:2/103.1

  Then be trimmed to: BBSDev#885:1,/1,/2,:885,fidonet#1,:2,
  /103,.1


6. Trimmed Lists
────────────────

  Some components of FTN such as PATH use "Trimmed Lists" of node
  addresses.  An empty list is encoded as an empty string.  A nonempty
  list uses the element construction and expansion rules from section
  5 without sorting or removing duplicates.  Every occurrence is
  retained.  When an address is identical to the immediately preceding
  address, its complete canonical address is emitted because removing
  every component would leave an empty list element.

  A canonical Trimmed List MUST reproduce the exact input bytes when
  it is expanded and constructed again.  An enclosing protocol may
  separately reject or diagnose a repeated address; this encoding does
  not remove one.

  Example: fidonet#1,fidonet#1:2,fidonet#1:2/103,BBSDev#885:1/1,
  fidonet#1:2/103.1,BBSDev#885,BBSDev#885:1,BBSDev#885:1/1,
  BBSDev#885:1/2

  Would be trimmed to: fidonet#1,:2,/103,BBSDev#885:1/1,
  fidonet#1:2/103.1,BBSDev#885,:1,/1,/2


7. Wildcards
────────────

  A wildcard allows specifying multiple addresses with a single
  string.  Any Component may be replaced with a wildcard, but there
  is an additional restriction on the Domain part, which may not
  specify a range.  If any components after a wildcard component are
  left off, they are assumed to be a single asterisk.

  The following wildcard components are supported:

  A single Asterisk (U+2A) which will match any value except −1 in the
  Component.

  A list, enclosed by a Less‐Than Sign (U+3C) and a Greater‐Than Sign
  (U+3E) containing a comma‐separated list of values.  For numeric
  Components, a value may be an inclusive range with the start and end
  value separated by a single Hyphen‐Minus (U+2D).

  Examples:
  ─────────
  * matches any node
  BBSDev#* matches any node in domain "BBSDev"
  BBSDev#*/0 matches any node in domain "BBSDev" with a Node of 0
  *:1 matches any node with a Net of one
  *#<885,1-6> matches nodes with a Zone of 885, 1, 2, 3, 4, 5, or 6
