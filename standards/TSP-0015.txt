Abstract
────────

  This document defines channel‐independent public key trust evidence,
  durable pins, effective key resolution, and authenticated continuity
  for non‐anonymous TITH identities.

1. Introduction
───────────────

  A non‐anonymous address identifies one system, but its signatures can
  be authenticated only when its signing public key is known.  An
  independently authenticated publication may supply that key in the
  ordinary case, while private networks, delayed publication, first
  contact, and planned rotation also require durable local trust state.
  As defined by TTS‑0004, either an authoritative listing or an
  effective local pin makes the identity listed for that implementation.

  This proposal defines that state once.  Discovery, configuration,
  and continuity mechanisms supply evidence to it; they do not define
  competing meanings for a pin or effective key.

  As nonnormative examples, TTS‑5000 currently supplies authoritative
  nodelist keys, TSP‑0002 authorizes one native first‐contact channel,
  TSP‑0014 supplies legacy observations, and TTS‑0005 supplies a
  predecessor‐signed continuity proof.  Those documents own the checks
  which make their particular inputs qualify as evidence.


2. Trust Evidence
─────────────────

  Trust evidence binds one canonical non‐anonymous address to one exact
  PublicKey and has one of these categories:

    Authoritative external anchor
      A binding obtained through a separately authenticated publication
      mechanism which its defining standard makes authoritative for the
      address.

    Authorized initial observation
      An observation from an exact contact which local policy explicitly
      designated as trusted while the identity had no existing anchor or
      pin.

    Authenticated continuity proof
      A proof authenticated by the exact effective predecessor which
      binds that predecessor and address to one exact successor key.

  The standard defining an input channel owns all parsing,
  authentication, identity, correlation, and authorization checks
  needed for its result to enter one of these categories.  An input
  which does not pass every such check supplies no trust evidence.

  A self‐signed key observed at a contacted endpoint proves possession
  of that key but does not prove that the endpoint belongs to the
  intended non‐anonymous address.  Such an observation is not an
  authorized initial observation unless the exact contact was
  explicitly trusted.


3. Trust Records
────────────────

  A conforming implementation which retains a key for a non‐anonymous
  address MUST store it in service‐owned durable state.  A record
  contains:

  • the canonical non‐anonymous address;
  • the current pinned PublicKey;
  • the authoritative PublicKey which anchored its continuity chain,
    if any;
  • the predecessor PublicKey for the latest authenticated advance, if
    any;
  • when the observation was accepted; and
  • whether the latest accepted evidence was an authorized initial
    observation or an authenticated continuity proof.

  An implementation may retain more detailed local provenance for an
  evidence channel, but that detail does not create another evidence
  category or change resolution.

  The update which advances a pin MUST be atomic.  A crash cannot leave
  a new current key without the record of the predecessor and evidence
  category which authorized it.  Pin state is private service data and
  MUST NOT depend on an outbound filename, scan order, or transient
  connection.


4. Effective Key Resolution
──────────────────────────

  A current authoritative external anchor is directly effective for
  its non‐anonymous address when no continuity record supersedes it.

  A continuity record anchored by that exact external anchor makes its
  current pinned key effective.  This permits an old published key to
  certify a planned successor before the external publication changes.
  If the authoritative source later publishes the successor, that key
  is directly effective and the older chain no longer needs to override
  it.

  If the authoritative source supplies a key unrelated to the record's
  anchor, that new anchor takes precedence.  A local observation MUST
  NOT override that new external trust decision.  With no authoritative
  anchor, an existing local pin is effective.  When neither exists, the
  identity has no effective key.

  This resolution produces at most one effective key.  Every TITH
  operation which needs the key of a non‐anonymous identity MUST use
  that result.  This includes Bundle Origin and Destination
  authentication, Message and standalone File Origin or SignedOrigin
  signatures, retained legacy signatures, signed‐item duplicate
  identity, and authorization policy.  After verification fails with
  the effective key, an implementation MUST NOT retry another key or
  fall back from Origin to SignedOrigin.

  An anonymous identity is the exact address and PublicKey pair defined
  by TTS‑0004.  Local policy may pin that exact identity and thereby
  list it, but this document does not prescribe how such a pin is
  represented.  Its accompanying PublicKey remains required on the
  wire.  A different PublicKey denotes a different anonymous identity,
  not a continuity advance, so the record and resolution rules above
  do not apply to anonymous identities.


5. Applying Evidence
────────────────────

  An authorized initial observation MAY establish a pin only while the
  identity has no authoritative anchor or existing local pin.
  Establishing the pin makes that identity listed for the
  implementation.  The implementation MUST log that a new trust
  decision was made.  Another initial observation MUST NOT replace an
  existing pin.

  An authenticated continuity proof MAY atomically advance a pin only
  when its predecessor is the exact effective key for that address.
  The successor becomes the current pin and the record retains the
  predecessor, evidence category, and current authoritative anchor, if
  any.

  Evidence authenticated by another key is not continuity evidence.  A
  newly observed key, repeated authentication failure, or an observation
  which conflicts with an existing decision MUST NOT replace the
  effective key.


6. Rotation and Revocation
──────────────────────────

  An operator planning rotation retains the old private key long enough
  to produce the authenticated continuity proof defined by an input
  channel.  A retained secret MUST be used only for that continuity
  proof and MUST NOT sign ordinary new traffic.

  This mechanism establishes continuity, not revocation.  If the old
  private key is compromised, an attacker can certify another key with
  the same authority.  Recovery then requires a trust decision outside
  this proof, such as a corrected authoritative external anchor, an
  administrative action, or another separately authenticated channel.
  Software MUST NOT describe a continuity advance as proof that the
  predecessor is uncompromised or revoked.


7. Feedback and Discussion
──────────────────────────

  Discussion of this proposal should occur in the repository issue
  tracker.  Reports should distinguish discovery, continuity, and
  compromise recovery because they have different trust properties.
