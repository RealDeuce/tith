1. Introduction
───────────────

  FTNs at their core exchange messages, files, and file requests.
  Historically, this has been done using dial‐up connections, and a
  large amount of infrastructure has been built up around that.  It is
  much more common, however, to use the internet to perform these three
  tasks, with the binkp protocol as implemented in the binkd program
  far and away the most common method to use.

  While the binkp protocol and binkd programs perform this job very
  well, the binkp protocol is complex enough that many third parties
  have introduced subtle standard‐breaking behaviour which must be
  allowed to preserve compatibility with the larger network.

  TITH is therefore defining a new protocol to avoid needing to test
  against all other implementations and add various workarounds.


2. Terminology
──────────────

  This section defines some terms used in the rest of the document.

  Client
  ──────
  The Client is the software that initiated the connection.  When
  using TCP with the BSD socket API, this means it is the software that
  called connect().  For a POTS connection, this is the software that
  dialed the phone number.

  Server
  ──────
  The Server is the software that was connected to.  When using TCP
  with the BSD socket API, this means it is the software that called
  accept().  For a POTS system, this is the software that answered the
  phone call.


3. Basic Design
───────────────

  The design goals of this new protocol are as follows:
  • The Client is in charge of the connection.  The Server only does
    anything in response to an explicit request by the Client.
  • The Client performs the active close.  For TCP, this means the
    TIME_WAIT state occurs on the client side.
  • It is clear when a Server has completely handled a request from
    the Client.
  • Anything the Server sends is clearly associated with a Client
    request.
  • A Server or Client may refuse something sent by the remote system.
    A Rejected value will indicate this.
  • Every Bundle Header and payload SignedTLV is authenticated before
    its contents are processed.  A Message or standalone File has the
    independent end‑to‑end authentication states defined by TTS‑0009;
    its Signature may be absent or invalid without weakening the
    authenticated SignedTLV which carried its exact bytes.
  • The Client must be able to send all of the bundles it has
    prepared, and never send another byte.

  Authentication of the anonymous address proves possession of its
  private key.  It does not establish membership in a network which
  uses a nodelist.  Except for the dedicated PublicKeyRequest exchange
  defined by TTS‑0005, a supplied PublicKey MUST NOT be used in place
  of the effective key for any non‐anonymous Origin.  TTS‑0008 defines
  how that key is resolved, pinned, and advanced.


4. Connection Flow
──────────────────

  For TCP, as soon as the connection is established, the Client is
  expected to start a single Bundle as described in TTS‑0005.  If the
  Bundle does not have a FileRequest or any Poll values in it
  (PollMessages, PollFiles, PollFileRequests), it SHOULD send a FIN on
  the socket.  For the BSD socket API, this means calling shutdown()
  with a how value of SHUT_WR.  If a FileRequest or any of the Poll
  values were present, the Client SHOULD receive a Reply Bundle from
  the Server and send a Reply Bundle in response to that, then shut
  down the connection.

  The Server will generate a Reply Bundle indicating what was accepted
  or rejected in the corresponding Bundle.  It may send the reply
  while still receiving the Bundle from the Client, but MUST NOT start
  the SignedTLV response until it has verified the signature of the
  SignedTLV in the Bundle from the Client.

  If no error is detected, the Client knows how many responses to expect
  from the values in the Bundle it sent.  The Server has completed its
  response when the Client has completely received and authenticated
  every SignedTLV containing the Accepted or Rejected response for each
  such value.  As specified in TTS‑0005, this also completes receipt of
  the values returned by an accepted Poll or FileRequest.  The Client
  MUST NOT wait for the Server to close its write side to determine that
  the response is complete.

  Replies may continue to go back and forth until a Reply Bundle is
  sent that does not have a FileRequest or Poll value in it.  If the
  Server sends this Bundle, it SHOULD try to wait for the Client to
  initiate the close.  Receipt of this Bundle does not omit the Client
  Reply Bundle described in the first paragraph when that paragraph
  calls for one.  The Client sends that Reply Bundle before closing its
  write side.

  If the Client sends a Bundle without a FileRequest or Poll value, it
  SHOULD send a FIN as described above after the complete Bundle.  The
  FIN closes only the Client's write side.  The Client continues reading
  until every response it expects for that Bundle has been completely
  received and authenticated, then closes the connection.  It does not
  use a Server FIN to determine that those responses are complete.

  A PublicKeyRequest uses a connection of its own.  The Client MUST
  send a Bundle containing only the dedicated request grammar in
  TTS‑0005 and then close its write side.  The Server MUST NOT use that
  connection for held or operational values.  After completely
  receiving and authenticating the reply, the Client closes the
  connection before opening an operational connection.

  When a non‐anonymous peer's reply fails authentication with the
  currently trusted key, the Client MAY make one PublicKeyRequest for
  that exact predecessor and then retry the original exchange once.
  The failed original exchange, the probe, and the one retry form one
  continuity‐recovery sequence.  The Client MUST accept the returned
  key only from a reply which supplies the authenticated continuity
  proof defined by TTS‑0005 before submitting that proof to TTS‑0008,
  persisting the key, or using it.  Failure of either the probe or the
  one retry ends that sequence; this rule does not create an unbounded
  retry loop.

  If the requested predecessor private key is unavailable, TTS‑0005
  requires a refusal signed by the Server's current key.  Because that
  reply cannot be authenticated with the requested predecessor, the
  Client MUST leave the PublicKeyRequest incomplete, MUST NOT submit
  either its Rejected value or current key as trust evidence, and MUST
  end the continuity‐recovery sequence.

  A first‐contact PublicKeyRequest omits the non‐anonymous Destination
  PublicKey.  A Client MUST do this only when its local configuration
  explicitly authorizes trust on first use for that contact and fixes
  the endpoint used.  A completely validated reply from that contact
  supplies the authorized initial observation defined by TTS‑0008.
  Receipt of a self‑signed response without that authorization is not
  evidence that the endpoint belongs to the intended operator.


5. Error Handling
─────────────────

  TTS‑0005 defines framing and data errors in a Bundle.  During a live
  exchange, the consequences of those errors are defined by this
  section rather than by the discard rules in TTS‑0005.

  When a framing error is detected, the receiver MUST stop processing
  and close the connection.  It MUST NOT attempt to find and resume at
  a later value.

  The first SignedTLV in a Bundle is its Header SignedTLV.  If it
  cannot be authenticated, or, ignoring permitted unknown values, its
  SignedData does not contain exactly one Destination, the conditionally
  required PublicKey specified by TTS‑0005, and exactly one Timestamp,
  the receiver MUST close the connection.  The unauthenticated request
  handling below does not apply to a Header SignedTLV.

  After authenticating the Header SignedTLV, the receiver MUST verify
  that its Destination identifies the receiver.  An anonymous address
  identifies the receiver only when its PublicKey also matches the
  receiver's public key.  For a Reply Bundle, the receiver MUST
  also verify the Origin, Destination, and PublicKey relationship
  specified in section 6 of TTS‑0005.  If any check fails, no value in
  the Bundle counts as a response and the receiver MUST close the
  connection.

  If an authenticated payload SignedTLV has a missing or incorrect
  Header TLVHash, any Accepted or Rejected value in it MUST NOT count
  as a response and the receiver MUST close the connection.  Requests
  in such a payload are handled as authenticated data errors below.

  Before processing or acting upon any request in one payload
  SignedTLV, or generating a response to one, the receiver MUST verify
  that its request values have distinct RequestIdentifiers.  If two
  request values have the same RequestIdentifier, the receiver MUST
  NOT process or act upon any request in that SignedTLV, MUST NOT
  generate a response to any of them, and MUST close the connection.
  This rule applies to both authenticated and unauthenticated
  SignedData.

  When a SignedTLV cannot be authenticated but its SignedData has
  valid TLV framing, the receiver MAY parse the SignedData only far
  enough to identify its request and response values and the
  RequestIdentifiers of its request values.  If the SignedData
  contains an Accepted or Rejected value, the receiver MUST NOT count
  that value as a response and MUST close the connection.  This takes
  precedence over generating responses for any request values in the
  same SignedData.

  If every request that requires a response has a valid
  RequestIdentifier, the receiver MUST generate a Rejected response
  with reason number 1 and no Timestamp for each request.  It MUST NOT
  otherwise process or act upon the unauthenticated contents.

  If unauthenticated SignedData does not have valid TLV framing, or a
  request in it that requires a response does not have a valid
  RequestIdentifier, the receiver MUST close the connection.

  When an authenticated and completely framed request has a data
  error but contains a valid RequestIdentifier, the receiver MUST
  generate a Rejected response with reason number 1 and no Timestamp
  for that request.  If the request does not contain a valid
  RequestIdentifier, the receiver MUST close the connection.

  These reason 1 responses do not change the independent end‐to‐end
  item authentication states defined by TTS‑0009.

  For the request types defined by TTS‑0005 and TTS‑0009, the receiver
  MUST NOT generate a Rejected response with reason number 2 except
  for a FileRequest which contains a Timestamp and whose condition is
  unmet.  A file last modified at a time equal to or older than the
  Timestamp does not satisfy the condition.

  Closing the connection because of an error does not undo any
  Accepted or Rejected responses already completed.  Requests for
  which no response was completed remain unacknowledged and may be
  included in a later Bundle.  If the sender lost a completed Accepted
  response or could not make that response durable before a failure,
  it MAY retransmit the same signed item.  The receiver MUST handle
  that item according to the duplicate acceptance rules in TTS‑0005.
  Receipt of a FIN or other connection termination before every
  expected response is complete MUST be treated as a failed exchange.

  Both the Client and Server SHOULD log errors with as much detail as
  practical.

B. History
──────────

   Rev.1, 2025‑12‑14: Initial Release.

   Rev.2, 2026‑08‑17: Clarified recovery when an Accepted response is
   lost or is not durable at the sender.

   Rev.3, 2026‑08‑18: Distinguished an item's originating and reply
   Origin from its fallback SignedOrigin authentication identity.

   Rev.4, 2026‑08‑18: Distinguished mandatory Bundle and payload
   SignedTLV authentication from optional end‐to‐end Message and File
   signatures.

   Rev.5, 2026‑08‑20: Defined the dedicated non‐anonymous‐key discovery
   exchange and a single same‐activation continuity retry.

   Rev.6, 2026‑08‑20: Distinguished anonymous address grammar from
   listing status and required the TTS‑0008 effective key for every
   non‐anonymous transport identity.

   Rev.7, 2026‑08‑21: Assigned permanent rejection reason 1 without a
   Timestamp to unauthenticated SignedData and authenticated request
   data errors.

   Rev.8, 2026‑08‑21: Required distinct RequestIdentifiers within each
   directional payload SignedTLV and removed any dependence on response
   order.

   Rev.9, 2026‑08‑22: Referred end‑to‑end Message and File
   authentication states to the data‑level Item Format proposal.

   Rev.10, 2026‑08‑22: Kept request‐specific uses of rejection reasons
   at the exchange edge while TTS‑0005 defines their shared retry
   semantics.

   Rev.11, 2026‑08‑22: Submitted completely validated first‐contact and
   continuity results to the channel‐independent TTS‑0008 trust model.

   Rev.12, 2026‑08‑22: Defined continuity recovery as a bounded exchange
   sequence independent of scheduling.

   Rev.13, 2026‑08‑23: Required an unavailable‐predecessor refusal to
   complete no response, produce no trust evidence, and end the bounded
   continuity‐recovery sequence.

   TSP Rev.1, 2026‑08‑28: Updated the normative Bundle Format
   dependency for the Libhydrogen interoperability profile set.
   Proposed as TTS‑0006 revision 14.
