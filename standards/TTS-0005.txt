  This document describes how assets are placing into a bundle for
  transfer to another system.

1. Introduction
───────────────

  One of the core capabilities needed for an FTN network is the
  ability to transfer data from one node to another.  This standard
  defines the format to be used for that transfer.


2. Encoding
───────────

  Data to be transfered between two nodes is collected into a single
  bundle for the transfer.  The entire bundle is TLV encoded as
  defined in TTS‑0002.

  The bundle as a whole is a sequence of TLV values as described in
  TTS‑0003.

  The first item MUST be an Origin as defined in TTS‑0003.  This Origin
  is applicable to the SignedTLV values that follow.  If it is the
  unlisted address defined in TTS‑0004, it MUST be immediately
  followed by a PublicKey as defined in TTS‑0003.  Otherwise it MUST
  NOT be followed by a PublicKey, except in the PublicKeyRequest reply
  defined below.  For the unlisted address, this
  PublicKey is the key applicable to the SignedTLV values that follow.
  For any other Origin, the applicable key is obtained from the
  nodelist or the trust state defined by TSP‑0015, and a supplied
  PublicKey MUST NOT override it.

  A reply to a PublicKeyRequest is the sole exception for a listed
  Origin.  Its Origin MUST be immediately followed by the PublicKey
  whose private key signs that reply.  The receiver MUST accept that
  key only when it is the key requested in the original Header, or
  when the request was an explicitly authorized first‑contact probe.

  Ignoring permitted unknown values, the next item MUST be a SignedTLV
  as defined in TTS‑0003.  This is the Header SignedTLV and MUST NOT
  contain an Origin.  Its SignedData MUST contain one Destination,
  followed by a PublicKey if the Destination is the unlisted address
  or the Bundle requests continuity from a listed predecessor key,
  followed by one Timestamp, all as defined in
  TTS‑0003.  A required PublicKey MUST be the encoded child immediately
  after its Destination.  The PublicKey identifies the particular
  unlisted system to which the Bundle is addressed.  For a listed
  Destination it identifies the already trusted predecessor key from
  which a PublicKeyRequest asks for continuity.  A listed Destination
  PublicKey is permitted only in a Bundle whose only request is one
  PublicKeyRequest.  The Timestamp
  indicates when the bundling process started and is not updated when
  another item is added to the Bundle.

  After the Header SignedTLV is a sequence of payload SignedTLV values.
  The SignedData in every payload SignedTLV MUST begin with a TLVHash
  of the complete encoded Header SignedTLV, followed by a sequence of
  the types defined in section 3 or one of the experimental reserved
  values 32 to 63.  A missing or incorrect Header TLVHash is a data
  error for the entire payload SignedTLV.  Payload SignedTLV values
  SHOULD NOT contain an Origin.

  In this document, “first” and “begins with” refer to the literal
  first encoded child, including when unknown types are present.  This
  applies to the Bundle Origin, the Origin that begins a Message, and
  the Header TLVHash that begins every payload SignedData.  A PublicKey
  whose presence depends on the immediately preceding address MUST be
  the next encoded sibling; an unknown value cannot separate the pair.

  After a required leading child and any conditional PublicKey,
  unknown TLV values MAY occur between or after the remaining defined
  children.  They do not change the relative order, cardinality, or
  requirements of defined children.  An unknown value cannot satisfy
  or replace a required child.  A type assigned by this document or
  TTS‑0003 but used in a position not permitted by the applicable
  grammar is a data error, not an unknown type.  Where a grammar does
  not designate a literal leading child, unknown values MAY also
  precede the first defined child.

  Types 32 to 63 are reserved for experimental extensions to this
  standard, and may be used by explicit agreement between the
  operators of two nodes.  If the use is useful to other operators, it
  is RECOMMENDED that it be added to this document with a new number,
  and the software using it modified to use the new value.  Basically,
  as soon as three node operators agree to use the same value, it
  should be added to this document and the experimental value
  abandoned.

  It is RECOMMENDED that there be no more than two payload SignedTLV
  values in each Bundle, with the first containing all FileRequest,
  PollMessages, PollFiles, and PollFileRequests values, and the next
  containing everything else.  If there are no FileRequest or Poll
  values, a single payload SignedTLV SHOULD be used.  The reason for
  this is to allow the destination node to validate the SignedTLV
  containing the FileRequests and start sending them while any Files
  or Messages are being sent from the Origin to the Destination.


3. Types
────────

  The following types may be included in a bundle.

  64. Message
  ───────────
  A Message value has a large number of manditory and optional values.
  The order is specified here as a list, with M indicating Manditory,
  O indicating Optional, N indicating Manditory for NetMail, E
  indicating Manditory for EchoMail, C indicating Optional for
  EchoMail and prohibited for NetMail, and A indicating Manditory if
  the immediately preceding address is the unlisted address and
  prohibited otherwise.  If a + is listed after the mandatory or
  optional character, multiple values of that type may be included.

  A Message MUST be either NetMail or EchoMail.  NetMail MUST contain
  a Destination and MUST NOT contain an Area.  EchoMail MUST contain
  an Area and MUST NOT contain a Destination or its following
  PublicKey.  TearLine and OriginLine are EchoMail control
  information in FTS‑0004.001 and FSC‑0068.001, and FTS‑0001.016
  defines neither, so NetMail MUST NOT contain either one.  A legacy
  NetMail which carries such a line carries it as message text.

  M  Origin (TTS‑0003)
  A  PublicKey (TTS‑0003)
  O  SignedOrigin (TTS‑0003)
  A  PublicKey (TTS‑0003)
  N  Destination (TTS‑0003)
  A  PublicKey (TTS‑0003)
  M  Timestamp (TTS‑0003)
  M  ToUserName (Section 4)
  M  FromUserName (Section 4)
  M  Subject (Section 4)
  M  MessageText (Section 4)
  E  Area (Section 4)
  O+ File (Section 3)
  O  LegacyAttributes (Section 4)
  O  TimestampOffset (Section 4)
  C  TearLine (Section 4)
  C  OriginLine (Section 4)
  O  MessageID (Section 4)
  O  ReplyTo (Section 4)
  O  OriginalCharacterSet (Section 4)
  O  Signature (TTS‑0003)
  M  RequestIdentifier (Section 4)
  M+ Via (Section 4)
  O  SeenBy (Section 4)
  O+ AdditionalKludgeLine (Section 4)

  When present, the Signature signs the exact encoded bytes of every
  child TLV preceding it, beginning with the Type of the Origin and
  ending with the final byte of the last child before the Signature.
  The Type and Length of the enclosing Message and the Signature
  itself are not signed.  Origin is the system where the Message
  originated and is the address used to construct a reply.  Its
  immediately following PublicKey is present if and only if Origin is
  the unlisted address.  For another Origin, its key is obtained from
  the nodelist when a Signature is present.

  SignedOrigin is permitted only when Signature is present.  If a
  public key is available for Origin, that key is applicable to the
  Signature and SignedOrigin is ignored for key selection.  An invalid
  Signature MUST NOT then be retried with SignedOrigin.  If no key is
  available for Origin, SignedOrigin MUST be present and its key is
  applicable.  Its immediately following PublicKey is present if and
  only if SignedOrigin is the unlisted address; otherwise its key is
  obtained from the nodelist.  The applicable address and key form the
  effective signer.  SignedOrigin does not replace Origin for a reply,
  MessageID, or routing to the Message's Destination.

  An absent Signature means that the Message has no end‐to‐end item
  authentication.  It does not make the Message malformed when its
  enclosing payload SignedTLV has been authenticated.  The Origin key
  need not be available, and SignedOrigin is prohibited.  Native
  forwarding software MUST NOT add, remove, or replace an item
  Signature.  A legacy conversion boundary may reconstruct or omit one
  only as specified by TSP‑0003.

  When Signature is present, its signed child values and the Signature
  MUST NOT be modified in transit.  RequestIdentifier, Via, SeenBy, and
  AdditionalKludgeLine values following it may be modified without
  invalidating it.  When Signature is absent, these values follow the
  last signed‐position child directly.  TSP‑0011 defines the final local
  disposition and user indication for every item authentication state.

  65. File
  ────────
  A File value has a large number of manditory and optional values.
  The order is specified here as a list, with M indicating Manditory,
  O indicating Optional, A indicating manditory for a File inside of a
  Message, T indicating manditory for a File not inside of a Message,
  directly inside of a SignedTLV, K indicating manditory if the
  immediately preceding Origin or SignedOrigin is the unlisted address
  and prohibited otherwise, and F for a file that is part of a
  distribution network.
  O  Filename (Section 4)
  O  Timestamp (TTS‑0003)
  M  Contents (Section 4)
  F  Area (Section 4)
  T  Origin (TTS‑0003)
  K  PublicKey (TTS‑0003)
  O  SignedOrigin (TTS‑0003)
  K  PublicKey (TTS‑0003)
  O  ShortDescription (Section 4)
  O+ LongDescriptionLine (Section 4)
  O  TearLine (Section 4)
  O  MagicWord (Section 4)
  O  Replaces (Section 4)
  O  Signature (TTS‑0003)
  T  RequestIdentifier (Section 4)
  F+ Via (Section 4)
  F+ SeenBy (Section 4)

  If a Signature is present, it signs the exact encoded bytes of every
  child TLV preceding it, beginning with the Type of the first child
  present and ending with the final byte of the last child before the
  Signature.  The Type and Length of the enclosing File and the
  Signature itself are not signed.  The File's Origin and optional
  SignedOrigin select the effective signer exactly as specified for a
  Message.  SignedOrigin is prohibited when the File has no Origin or
  Signature.  A standalone File MAY omit Signature.  It then has no
  end‐to‐end item authentication, and its Origin key need not be
  available.

  When Signature is present, its signed child values and the Signature
  MUST NOT be modified in transit.  RequestIdentifier, Via, and SeenBy
  values following it may be modified without invalidating it.  When
  Signature is absent, those values follow the last signed‐position
  child directly.

  A File directly inside a payload SignedTLV has its own Origin and
  optional Signature so its item authentication remains applicable
  when the File is placed in a new Bundle.  A File inside a Message
  does not require its own Signature because its complete encoded value
  is covered when the Message has a Signature.  An attached File MAY
  still contain an Origin, optional SignedOrigin, and Signature to
  establish independent provenance.

  If a timestamp is present, it represents the time of last
  modification of the file.

  The file values were chosen to allow replacing tick files.

  66. FileRequest
  ───────────────
  A Request value which contains a manditory Filename as defined in
  section 4, optionally followed by a Timestamp as defined in
  TTS‑0003, and followed by a manditory RequestIdentifier.  If a
  Timestamp is present, the request is conditional on the last
  modified time of Filename being newer than the Timestamp.

  Existing FidoNet requests types (Bark and WaZOO) have an optional
  password, but it is expected that having public key authentication
  should be both more secure and easier to administer, making password
  controlled file requests obsolete.

  The WaZOO request can also request files the same age or older than
  the timestamp.  The author can't come up with a reasonable use for
  this, so is not including that functionality initially.

  Finally, WaZOO requests allow wildcards, which means the requester
  does not know the name of the file they're requesting, or how many
  files they are requesting.  However, since the Filename value is
  unrestricted, it's not like I can stop you can allowing wildcards
  in there.  I think it's a terrible idea though, and the processors
  written as part of the TITH project won't support them.

  67. Rejected
  ────────────
  A Rejected value which contains a manditory RequestIdentifier as
  defined in section 4, followed by a manditory TLVHash as defined in
  section 4, followed by an optional Timestamp as defined by TTS‑0003,
  followed by a manditory number encoded in the same manner as Type
  and Length, optionally followed by a UTF‑8 string containing a
  human‐readable description of why the request was rejected.

  This is included because a Message, File, or FileRequest from
  Destination to Origin was not accepted.

  The RequestIdentifier is the the one that was in the original
  Message, File, or FileRequest.

  If a Timestamp is present, indicates an expected time at which the
  same request would not be Rejected.

  The number may have one of the following values:

  1 — Indicates that in the current configuration, the TLV value would
      always be Rejected.  Including it in a future bundle would also
      be rejected.
  2 — Indicates that the TLV could not be authenticated.  The receiver
      did not process or act upon its unauthenticated contents.
  3 — Indicates that the TLV was conditional, and the condition was
      not met.  For example, if a Timestamp was included in a
      FileRequest, but the last modified time of the requested file
      matches the value of the Timestamp.  If a Timestamp is included
      in the Rejected value, this is a time at which it is expected
      that the request would not be Rejected.
  4 — Indicates that the node is not willing to accept the TLV value
      at this time.  If a Timestamp is included in the Rejected value,
      this is a time at which the node expects to be willing to accept
      the TLV value.

  68. Accepted
  ────────────
  An Accepted value which contains a manditory RequestIdentifier as
  defined in section 4, followed by a manditory TLVHash as defined in
  section 4, and, only when accepting a PublicKeyRequest, followed by
  exactly one PublicKey.  It indicates that the identified value has been
  validated.  Except for PublicKeyRequest, it also indicates that the
  value was either durably stored by the receiver or recognized as a
  previously accepted duplicate as specified in section 7.  For a
  PublicKeyRequest, the following PublicKey is the accepted result.

  69. PollMessages
  ────────────────
  A PollMessages value contains a manditory RequestIdentifier and
  requests held Messages committed to the Bundle Origin.

  70. PollFiles
  ─────────────
  A PollFiles value contains a manditory RequestIdentifier and
  requests held standalone Files committed to the Bundle Origin.

  71. PollFileRequests
  ────────────────────
  A PollFileRequests value contains a manditory RequestIdentifier and
  requests held FileRequests committed to the Bundle Origin.

  72. PublicKeyRequest
  ────────────────────
  A PublicKeyRequest contains one manditory RequestIdentifier and no
  other child.  It asks the listed Destination for its current public
  key.  It MUST be the only request in the Bundle, MUST be in the only
  payload SignedTLV, and that SignedTLV MUST contain only its leading
  Header TLVHash and the PublicKeyRequest.  It MUST NOT be combined
  with operational work or a Poll.

  When the listed Destination PublicKey is present in the Header, the
  Server MUST sign the reply with that exact key.  It MAY use a
  retained private key for this reply even though that key is no
  longer current.  When it is absent, the request is a first‑contact
  probe and the Server signs with its current key.

  When the Destination accepts a Poll value, it MUST atomically claim
  every matching held value which is not already claimed for an active
  exchange.  This complete claimed set is the poll snapshot.
  Every value in the poll snapshot MUST be returned in the same
  SignedTLV as the Accepted value as specified in section 6.  An empty
  poll snapshot is accepted with no returned values.

  A value committed after the atomic claim is not in that poll
  snapshot and remains available for a later exchange.  A value
  already claimed for an active exchange is likewise excluded and
  remains claimed for that exchange.  The Destination MUST NOT select
  only part of the otherwise available matching set.

  A held value matches only when it is held for the authenticated
  identity represented by the Bundle Origin.  For an unlisted Origin
  this identity includes the top‐level PublicKey.

  A node that holds a Message, File, or FileRequest for the unlisted
  address MUST retain the associated PublicKey as local delivery
  metadata.  When a Message is held for its ultimate Destination, this
  is its Destination PublicKey.  When it is held for an unlisted next
  hop, this is the next hop's PublicKey.  This local association is not
  added to or substituted for any PublicKey in the held value.


4. Ancillary Types
──────────────────

  The following types are defined for use by types in section 3.

  96. Filename
  ────────────
  The value is a UTF‑8 string containing the name of the file.  No
  restrictions are placed on the value of this string, but the name
  MUST NOT contain additional path components.  Software SHOULD NOT
  use values that are not allowed by common operating systems.
  Commonly this means no control characters (U+00 to U+1F, and U+7F),
  and none of U+22 ('"'), U+2A ('*'), U+2F ('/'), U+3A (':'),
  U+3C ('<'), U+3D ('>'), U+3F ('?'), U+5C ('\'), or U+7C ('|').

  97. Contents
  ────────────
  An arbitrary sequence of bytes with no restrictions on contents or
  length.

  98. RequestIdentifier
  ─────────────────────
  Contains a number encoded using the same method as the Type and
  Length values as defined by TTS‑0002.  This number MUST be unique
  for each SignedTLV from the Origin to the Destination, and is used
  to correlate a status or file from the Destination with a specific
  request.

  99. TLVHash
  ───────────
  Contains a 32‑byte unkeyed hash generated by the libhydrogen generic
  hash functions.  The context is the eight bytes of the C string
  "HashTLV", including the trailing NUL, and the key is NULL.

  The input to the hash is one complete encoded SignedTLV, beginning
  with the first byte of its Type and ending with the final byte of its
  Value.  This includes the encoded Type and Length of the SignedTLV
  and all bytes of its value, including any Origin, SignedData, and
  Signature values present.  The bytes MUST be hashed exactly as
  transmitted and MUST NOT be decoded and re‐encoded before hashing.

  A TLVHash at the beginning of a payload SignedData contains the hash
  of the Header SignedTLV for that Bundle.  A TLVHash in an Accepted or
  Rejected value contains the hash of the payload SignedTLV that
  contained the original request.

  Every Accepted or Rejected response to a request in the same
  SignedTLV contains the same TLVHash.  The RequestIdentifier selects
  the individual request within that SignedTLV.  Together these values
  bind the response to the precise signed transmission and prevent a
  response to a different SignedTLV from being replayed as its status.

  100. Unassigned
  ───────────────
  This type is not supported and MUST NOT be generated.  Its number is
  available for assignment by a future revision of this standard.

  101. LegacyAttributes
  ─────────────────────
  Contains a number encoded the same as the Type and Length values.
  Its only permitted bits have these AttributeWord meanings from
  FTS‑0001.016:

    bit 0   Private
    bit 1   Crash
    bit 12  ReturnReceiptRequest
    bit 13  IsReturnReceipt
    bit 14  AuditRequest

  These are the packet‐persistent legacy message attributes.  All
  other AttributeWord bits are either redundant native facts or
  mutable legacy bookkeeping and transport state, and MUST NOT be set
  in this value.

  A zero conveys nothing that the absence of this value does not, so
  a zero MUST NOT be emitted and an absent value means that no legacy
  attribute is asserted.  In particular, bit 4, FileAttached, is
  represented by the File children of the Message; a legacy conversion
  boundary sets that bit from the File children it emits.

  102. TimestampOffset
  ────────────────────
  Contains a signed number of seconds encoded as specified in
  TTS‑0007.  If this number is added to the Timestamp, the result is
  the local time and date when the message was written.

  A zero conveys nothing that the absence of this value does not, so
  a zero MUST NOT be emitted and an absent value means that the offset
  is zero.

  103. ToUserName
  ───────────────
  Contains a UTF‑8 string which is a user name on the destination
  system.

  104. FromUserName
  ─────────────────
  Contains a UTF‑8 string which is a user name on the origin system.

  105. Subject
  ────────────
  Contains a UTF‑8 string which is the subject of the message.

  106. MessageText
  ────────────────
  Contains a UTF‑8 string which is the contents of the message.

  The string is zero or more paragraphs, each terminated by one U+000A.
  It is therefore either empty or ends in U+000A, and the number of
  U+000A values equals the number of paragraphs.  U+000A terminates a
  paragraph; it does not separate one paragraph from the next, and a
  final paragraph is terminated like every other.

  U+000D MUST NOT appear.  A producer which has a carriage return, a
  line feed, or a carriage return and line feed pair emits one U+000A
  for it, so that one line break has one representation.  This matches
  FTS‑0001.016, in which a hard carriage return "marks the end of a
  paragraph", and lets a legacy conversion map each terminator to one
  hard carriage return and back without inventing or discarding a byte.

  107. Area
  ─────────
  Contains an AreaName value optionally followed by an AreaDescription
  value.

  108. AreaName
  ─────────────
  Contains a UTF‑8 value which specifies which area the message is in.
  This likely has a lot of legacy restrictions that I can't find in
  any official document when used with legacy FTN software.

  109. AreaDescription
  ────────────────────
  Contains a UTF‑8 value which provides a description of the area for
  use when automatically adding areas.

  110. TearLine
  ─────────────
  Contains a UTF‑8 value which is "an optional program specifier".
  There is no "---" prefix in this value.

  111. OriginLine
  ───────────────
  Contains a small amount of information about the system where the
  message originated. The string SHOULD end with the node address in
  parenthesis.  The " * Origin: " part is not included.

  112. SeenBy
  ───────────
  Optional and only barely useful. Contains a Trimmed Collection of
  addresses as specified in TTS‑0004.  This collection is every system
  that is expected to have received this message.

  113. Via
  ────────
  A Via value contains a required Address, followed by a PublicKey if
  and only if the Address is the unlisted address, followed by a
  required Timestamp and a required UTF‑8 string.  The string MAY
  contain the program name and version separated by a space.

  The PublicKey identifies the particular unlisted system represented
  by the Via.  It is path metadata and does not override a nodelist key
  or authenticate any other value.

  The system originating a Message or distribution File MUST append a
  Via for itself before first committing the item to a next hop.  Each
  forwarding system MUST likewise append one Via for itself before
  committing a new next hop.  Existing Via values MUST NOT be removed,
  reordered, or modified.  Repackaging or retrying an item for the same
  committed next hop MUST NOT append another Via.

  114. MessageID
  ──────────────
  Contains a UTF‑8 string that uniquely identifies the message and the
  Origin system.

  115. ReplyTo
  ────────────
  Contains a required Address followed by a required UTF‑8 string that
  was copied from the MessageID of a message that this one is a reply
  to.

  116. OriginalCharacterSet
  ─────────────────────────
  Contains a UTF‑8 string that indicates a previous value of the CHRS
  control paragraph.  The Message will have been converted from this
  to UTF‑8 before it was placed in a bundle.

  117. AdditionalKludgeLine
  ─────────────────────────
  Contains a UTF‑8 string.  This string represents a control paragraph
  and would be added to a legacy message. The CTRL‑A character is not
  present.

  118. ShortDescription
  ─────────────────────
  Contains a UTF‑8 string which describes the File. This SHOULD be no
  more than 45 characters, and MUST NOT contain newlines.

  119. LongDescriptionLine
  ────────────────────────
  Contains a UTF‑8 string for each line of a multi‐line description.
  Each line SHOULD be no more than 45 characters, and MUST NOT contain
  newlines.

  120. MagicWord
  ──────────────
  Contains a UTF‑8 string indicating a potential alias for requesting
  the file with.

  121. Replaces
  ─────────────
  Contains a UTF‑8 string with wildcard characters '*' and '?' to
  select files this replaces. It is expected that configuration around
  sources and signatures be available.


5. Error Handling
─────────────────
  When processing a bundle, errors can fall into two categories,
  framing and data.

  A framing error occurs in the TLV parsing where the Type or Length
  is not properly encoded, or the Value is not long enough.  When a
  framing error occurs, the software MUST NOT attempt to process past
  the offset in the bundle where the error occured, and if it occurs
  inside a SignedTLV, the entire SignedTLV must be rejected.
  Processing should be the same as if the SignedTLV (if any) and
  everything after it was not present in the bundle.

  A data error occures because a Value field contains an error.  If
  this occurs before the first SignedTLV value, it MUST be handled as
  a framing error.  If this occurs in a SignedTLV value, the
  processing MUST be identical to processing the same Bundle without
  the SignedTLV value that contains the error.  Missing required
  values, and having values in the wrong order are data errors.

  An unknown type in a position permitted by section 2 is not an
  error.  While it is encouraged to log a message indicating that an
  unknown type is used, every permitted unknown value MUST be ignored
  semantically and retained byte for byte.  The rule applies only to
  values specified entirely as sequences of encoded TLV children.  It
  does not cause bytes in a mixed grammar, such as the raw integer and
  UTF‑8 string suffix of Rejected, to be interpreted as TLV values.


6.  Reply Bundles
─────────────────

  A Reply Bundle is generated in response to exactly one other Bundle.
  Its top‐level Origin MUST be the Destination from the Header of the
  Bundle to which it replies.  The Destination in its Header MUST be
  the top‐level Origin of that Bundle.  When the Reply Bundle's Origin
  is the unlisted address, it MUST be followed by the same PublicKey
  that followed the Destination in the original Bundle's Header.  When
  the Reply Bundle's Destination is the unlisted address, it MUST be
  followed by the same PublicKey that followed the top‐level Origin of
  the original Bundle.

  For each value in the Bundle of the types Message, File, FileRequest,
  PollMessages, PollFiles, PollFileRequests, and PublicKeyRequest,
  exactly one Accepted or Rejected value is included in the same order
  as in the original Bundle.

  A PublicKeyRequest reply MUST use the listed Origin PublicKey rule
  in section 2 and MUST contain exactly one payload SignedTLV.  Its
  Accepted value MUST contain the Server's current PublicKey.  Thus a
  reply signed by the requested predecessor certifies the successor
  carried inside its authenticated SignedData.  This proof establishes
  continuity only; it is not revocation of the predecessor or evidence
  that the predecessor was not compromised.

  When a Poll or FileRequest is Accepted, every value returned in
  response to it MUST be in the same SignedTLV as its Accepted value.
  The returned values and the Accepted value may occur in any order
  within that SignedTLV.  The end of the SignedTLV therefore marks the
  end of the returned values; no count is required.  In particular, an
  Accepted FileRequest does not require exactly one File: zero or more
  Files may be returned.

  The sender of the original Bundle therefore knows how many responses
  to expect.  An Accepted or Rejected response is not complete until
  its enclosing SignedTLV has been completely received and
  authenticated.  Once this has occurred for the response to every such
  value, the Reply Bundle is complete.


7. Duplicate Acceptance
───────────────────────

  A Message or standalone File whose Signature validates has a stable
  signed‐item identity.  This identity consists of the item type, its
  effective signer address and PublicKey, and its end‐to‐end Signature.
  The effective signer is Origin when its key is available and
  SignedOrigin otherwise.  A listed effective signer uses its nodelist
  key; an unlisted effective signer uses its accompanying PublicKey.

  The RequestIdentifier, Via, SeenBy, and AdditionalKludgeLine values
  following the Signature MUST NOT be part of the duplicate identity.

  The end‐to‐end Signature MUST be validated before its identity is
  used for duplicate acceptance.  When first accepting an item, the
  receiver MUST make the item and its duplicate identity durable
  before returning Accepted.  The receiver MUST retain the identity
  and MUST NOT expire it automatically.  An explicit administrative
  operation MAY remove retained identities; doing so permits a later
  retransmission to be accepted as a new item.

  When the receiver is presented with an identity it has already
  accepted, it MUST NOT store, import, or forward the item again.  It
  MUST return Accepted containing the RequestIdentifier and TLVHash
  applicable to the current transmission.  This permits a sender to
  retry an item whose earlier Accepted response was lost or was not
  made durable locally.

  A File inside a Message is covered by the Message identity.  A File
  directly inside a payload SignedTLV uses its own Origin and
  Signature.  Poll and FileRequest values are repeatable requests and
  do not use signed‐item duplicate identities.
