## Conformance roles and features

| Role | Mandatory features | Optional or conditional features |
| --- | --- | --- |
| TCP Client | Send one initial Bundle, account for every response, keep the write side open only when return traffic requires a Reply Bundle, actively close, and never use Server FIN as completion | Any number of alternating Reply Bundles; FileRequest and all three Poll kinds; first contact; one bounded continuity-recovery sequence |
| TCP Server | Authenticate before action, produce one correlated response per request, stream completed responses without whole-Bundle buffering, carry and resolve held values, and leave active close to the Client | Any number of alternating Reply Bundles; empty or nonempty Poll/FileRequest results; retained-predecessor proof or current-key refusal |
| Bundle receiver | Enforce framing, Header authentication and identity, Header-hash correlation, distinct directional identifiers, response accounting, and every section‑5 close or rejection disposition | Limited unauthenticated parsing solely for reason‑1 responses; permitted unknown values |
| Operational request processor | Independently accept or reject each authenticated request and preserve completed outcomes across a later failure | Conditional reason‑2 FileRequest rejection; local request policy remains outside the protocol |
| Continuity Client | Authenticate and correlate a dedicated reply before submitting trust evidence, never accept a current-key refusal as evidence, and bound recovery to one probe and one retry | Recovery is invoked only after an otherwise incomplete non-anonymous authentication failure |
| Continuity Server | Isolate a dedicated PublicKeyRequest connection and sign its exact reply with the requested predecessor when available | Refuse under the current key when the predecessor secret is unavailable |
| First-contact Client/Server | Use the dedicated exchange and require a completely validated self-signed result | Client support is gated by explicit trust-on-first-use authorization for one fixed endpoint |

Every named optional or conditional protocol path is implemented. Internal
FileRequest catalogue policy is not a TTS‑0006 feature: the implementation can
carry, reject, and complete FileRequests and can return zero or more Files,
while issue #19 separately proposes one application which might select them.

## Security review

The untrusted boundary is the byte stream at either end of every connection.
The common framing reader distinguishes clean EOF only where the state permits
it and rejects truncated type/length integers, incomplete bodies, invalid
nesting, prohibited defined top-level values, and attempts to begin another
Bundle before the current round is complete. It never scans for a later value
after an error. Tests exercise each initial-prefix failure, each signed payload
boundary, early FIN, trailing data, and a new Bundle prefix in an incomplete
round.

No Header contents are used before Header signature and grammar validation.
The destination must be the exact local identity, including the key of an
anonymous address. Reply Origin and Destination are reversed and validated
before any Accepted or Rejected value counts. Each payload signature and its
exact Header hash are validated before normal request dispatch. A wrong hash
cannot complete a response; its authenticated requests receive only their
specified data-error disposition.

Request identifiers are preflighted across the whole SignedTLV before any
request is acted on. Duplicates therefore cannot cause a partial side effect.
Unauthenticated data is parsed only through the isolated classification path;
it cannot dispatch an item, count a response, or generate anything except a
reason‑1 rejection for a well-framed request with a valid identifier. A
response mixed into unauthenticated data closes the connection and takes
precedence over all such rejections. Positive and negative tests independently
exercise authentication, framing, identifiers, response presence, and hash
correlation.

Completed authenticated responses survive a later connection failure, while
uncompleted requests remain retryable. Accepted duplicate identities are
durable under TTS‑0005, so retransmission after a lost response cannot repeat
the stored/imported/forwarded action. Poll snapshots remain held until their
returned values receive completed responses; every failure path releases or
preserves the hold according to whether responsibility transferred.

Non-anonymous authentication has one effective TTS‑0008 key. Ordinary traffic
never trusts an accompanying replacement key. Continuity recovery is isolated
to a dedicated connection, exact predecessor request, authenticated and fully
correlated proof, and one retry. An unavailable-predecessor reply is deliberately
signed by the current key, which makes it unusable under the requested
predecessor and yields no trust evidence. First contact requires explicit
configuration of the exact endpoint before a self-signed result can reach the
trust service. Tests cover wrong signers, keys, identities, hashes,
identifiers, reply shapes, unauthorized first contact, and bounded failure.

The Client determines completion from authenticated response accounting and
actively closes; it cannot be induced to wait for Server FIN. The Server can
poll or otherwise answer before its last earlier response and can process an
unbounded number of valid alternating rounds, but no whole-Bundle buffering or
protocol-sized allocation limit was added. Rust integer/TLV layers reject
unrepresentable lengths before allocation under their qualified standards.
