## Conformance roles and features

| Role | Mandatory features | Optional or conditional features |
| --- | --- | --- |
| Trust service | One durable canonical record, atomic advances, authoritative precedence, and at most one effective key | Authorized initial observation and authenticated continuity are both implemented |
| Evidence-channel consumer | Accept only a qualified category and refuse conflicting, unrelated, or anonymous evidence | Channel-specific provenance beyond the required category is implementation-private |
| Effective-key consumer | Use the one result for every non-anonymous authentication, identity, routing, and authorization decision; never retry another key after failure | Exact anonymous pins are represented by their existing address-and-key identity |
| Rotating operator/server | Retain a predecessor only for a continuity proof and never describe continuity as revocation | The implementation supports retained predecessor secrets and planned successors |

The open-ended permission to retain additional local provenance is
implementation discretion, not a separately named protocol capability. The
reference implementation nevertheless retains the required generic evidence
category and observation time.

## Security review

The trust boundary is the transition from channel-specific authenticated
evidence into the durable key-pin store. The store accepts a typed canonical
non-anonymous address and exact fixed-size public keys; anonymous addresses
are rejected. Input-channel code must authenticate and correlate evidence
before calling it. Native first contact additionally requires explicit policy
for the exact configured contact. A merely self-signed endpoint therefore
cannot create a pin through an ordinary connection.

The record and its transition are one redb transaction. Failed validation,
wrong predecessors, conflicting observations, corrupt records, and crashes
cannot expose a partially advanced current key. The stored anchor and
predecessor make the decision reconstructable after restart. The tests reopen
the database, reject every malformed encoding, and prove rejected updates
leave the prior record effective.

Authoritative state always enters resolution afresh. For A→B→C under anchor
A, C is effective; publication of B makes B directly authoritative, and a
later already-authenticated B→C proof may advance from B again. The trust
engine does not depend on how long a live server retains B. Evidence from A
after B becomes authoritative is rejected, and an unrelated authoritative
key wins over the old chain.

Every non-anonymous key consumer receives the resolver's single result.
Bundle and item verification do not try another key after failure, and an
effective Origin blocks SignedOrigin fallback. Routing hierarchy, relay Via,
authorization, retained signatures, and duplicate identity use the same
result. Anonymous identities remain exact address/key pairs and cannot enter
the non-anonymous continuity store.

The live continuity witnesses now include a Poll whose stale-key exchange
must close before a dedicated probe. TTS‑0006's replacement record pins the
native Windows positive stress runs and original-source negative control.
Socket failure never supplies trust evidence, and the probe and retry must
both succeed before the delivery and effective-pin assertions can pass.

A predecessor secret is selected only by the dedicated continuity-probe
reply. Normal traffic and the live local identity use the current secret even
while an authoritative publication is stale. Continuity records contain no
revocation state and no diagnostic claims that the predecessor is safe or
revoked; compromise recovery remains an external trust decision.
